    8. Authentification et autorisation

    Deux questions distinctes se posent pour chaque requête :

    • qui est l'utilisateur ? C'est l'authentification : il s'est identifié par un login et un mot de passe, et chaque requête suivante doit prouver qu'elle vient de lui ;
    • a-t-il le droit d'accéder à cette page ? C'est l'autorisation : dans l'étude de cas, seul un utilisateur de rôle ADMIN gère les médecins et les clients.

    La preuve d'identité doit voyager avec chaque requête. [Django] possède une application d'authentification complète, [django.contrib.auth] : un modèle [User] (une table de la base), un middleware qui range l'utilisateur connecté dans [request.user], des vues de connexion et de déconnexion, des permissions, des groupes, et l'interface d'administration qui les gère. Elle range l'utilisateur connecté dans sa session (chapitre sur les portées), ce qui est la solution la plus simple pour une application web. L'étude de cas, dans toutes ses versions ([ASP.NET Core MVC], [Spring MVC], [NestJS], [Flask], [Laravel], [Symfony]), utilise plutôt un jeton JWT (JSON Web Token), que nous garderons ici : après la connexion, le serveur fabrique un jeton qui contient l'identité de l'utilisateur et le signe avec une clé secrète (c'est le principe du cookie signé de l'exemple 23). Le jeton est déposé dans un cookie ; le navigateur le renvoie à chaque requête ; le serveur vérifie la signature. L'utilisateur peut lire son jeton, mais pas le modifier : toute modification rend la signature invalide. Le format est normalisé (RFC 7519), compris par tous les langages, et le jeton porte sa date d'expiration. Surtout, le serveur n'a rien à mémoriser : n'importe quel serveur qui connaît la clé peut vérifier le jeton.

    Les utilisateurs de l'étude de cas sont ceux de sa propre table [users], et non ceux de [django.contrib.auth] ; les jetons, eux, n'ont pas de place dans [django.contrib.auth]. Nous écrirons donc nous-mêmes l'authentification, avec les outils que nous connaissons déjà, ce qui a l'avantage de tout montrer :

    • un middleware (exemple 03) établit, pour chaque requête, qui est l'utilisateur, d'après le jeton de son cookie, et le range dans la requête ([request.utilisateur], exemple 12). Le reste de l'application ne voit que ce résultat ;
    • des décorateurs (exemple 08) protègent les vues : [@connexion_requise], [@role_requis("ADMIN")] ;
    • les mots de passe sont vérifiés par les fonctions de hachage de [Django] ([django.contrib.auth.hashers], utilisables sans le reste de l'application [auth]) ;
    • les refus d'accès sont des exceptions [PermissionDenied], transformées en page d'erreur par une vue [handler403] (exemple 24) ;
    • les tentatives de connexion sont limitées à l'aide du cache de [Django] (exemple 27).

    La fabrication et la vérification des jetons sont confiées à la bibliothèque [PyJWT], la plus utilisée en [Python], installée par le fichier [requirements.txt] des exemples (elle s'importe sous le nom [jwt]). (Il existe des bibliothèques de jetons JWT pour [Django], comme [djangorestframework-simplejwt], conçues pour les API ; pour une application web, quelques lignes suffisent, et elles montrent mieux le mécanisme.)

from dataclasses import dataclass, field


@dataclass(frozen=True)
class Utilisateur:
    login: str
    nom: str
    # le rôle : USER ou ADMIN
    role: str
    # le HACHAGE du mot de passe (vide pour un utilisateur lu dans un jeton)
    hachage_mot_de_passe: str = ""
    # le contenu du jeton qui a authentifié l'utilisateur ; field(default_factory=dict) :
    # un NOUVEAU dictionnaire vide pour chaque objet
    claims: dict = field(default_factory=dict)


# on ne conserve JAMAIS un mot de passe, seulement son hachage, calculé une fois pour
# toutes par la fonction make_password de Django (algorithme PBKDF2-SHA256, 1 500 000
# itérations, un sel aléatoire) :
# python -c "from django.conf import settings; settings.configure();
#            from django.contrib.auth.hashers import make_password; print(make_password('marie'))"
UTILISATEURS = {
    "marie": ("Marie Pélissier", "USER",
              "pbkdf2_sha256$1500000$pjnFn2tL1G4bu5rVFTv6sZ$Y6v+fj3dC+Y0LZYJGxeE1OOi9beaZVuMVm6R6tljEwI="),
    "admin": ("Administrateur", "ADMIN",
              "pbkdf2_sha256$1500000$UTT2hXVaLIEAuGHPFxgnv9$D9+Owt9lDG14VrvArR3n0GGQXWjY9Sg8cgFwip4+yx4="),
}


def chercher(login: str) -> Utilisateur | None:
    if login not in UTILISATEURS:
        return None
    # le "déballage" d'un tuple : ses trois éléments dans trois variables
    nom, role, hachage = UTILISATEURS[login]
    return Utilisateur(login, nom, role, hachage)
    • lignes 7-17 : un utilisateur : le login, le nom, le rôle, le hachage du mot de passe, et le contenu du jeton qui a authentifié l'utilisateur (vide pour un utilisateur lu dans la liste des utilisateurs). Les deux derniers attributs ont une valeur par défaut. Pour un dictionnaire, cette valeur ne peut pas être écrite [claims: dict = {}] : ce dictionnaire serait créé une seule fois, et partagé par tous les objets. [field(default_factory=dict)] demande à [@dataclass] d'appeler [dict()] pour chaque nouvel objet ;
    • lignes 20-24 : un serveur ne conserve jamais un mot de passe, même chiffré : si la base de données était volée, les mots de passe le seraient aussi (et beaucoup de gens utilisent le même partout). Il conserve le résultat d'une fonction de hachage, une fonction à sens unique : on peut calculer le hachage d'un mot de passe, mais pas retrouver un mot de passe à partir de son hachage. Pour vérifier un mot de passe saisi, on calcule son hachage, et on le compare à celui qui est enregistré ;
    • lignes 25-30 : deux utilisateurs de test, écrits dans le code (l'exemple 28 et l'étude de cas les mettront dans une base de données) : pour chaque login, le nom, le rôle, et le hachage du mot de passe. Le hachage a été calculé une fois pour toutes par la fonction [make_password] de [Django] (la commande est donnée en commentaire), avec son algorithme par défaut, PBKDF2-SHA256. Le hachage enregistré a quatre parties, séparées par des [$] : l'algorithme ([pbkdf2_sha256]), le nombre d'itérations, le sel, puis le résultat. Un bon algorithme de hachage de mots de passe a deux particularités. Il est volontairement lent, d'une lenteur réglable : PBKDF2 applique 1 500 000 fois la fonction SHA-256, ce qui prend quelques centaines de millisecondes, imperceptibles pour un utilisateur, mais rend très coûteux l'essai de milliards de mots de passe par un pirate ; [Django] augmente ce nombre à chaque version, pour suivre la puissance des ordinateurs (son application [auth] met alors à jour les hachages enregistrés, lors des connexions) ; les anciens hachages restent vérifiables, puisqu'ils portent leur nombre d'itérations. Il est salé : un sel, tiré au hasard, est mélangé au mot de passe avant hachage, et rangé dans le hachage lui-même ; deux utilisateurs qui ont le même mot de passe ont ainsi des hachages différents. [Django] sait aussi utiliser [Argon2] et [bcrypt] (réglage [PASSWORD_HASHERS]) ; l'étude de cas, dont la base contient des hachages [bcrypt], utilise directement la bibliothèque [bcrypt] ;
    • lignes 33-38 : l'utilisateur d'un login, ou [None]. [not in] teste l'absence d'une clé ; l'affectation [nom, role, hachage = ...] déballe un tuple : chaque variable reçoit l'élément correspondant.

    # securite/auth.py : la vérification des mots de passe et les jetons JWT

import time

import jwt
from django.conf import settings
from django.contrib.auth.hashers import check_password

from . import utilisateurs
from .utilisateurs import Utilisateur

# le nom du cookie qui transporte le jeton
COOKIE = "jeton"


# l'utilisateur, ou None si le login est inconnu ou le mot de passe faux.
# check_password hache le mot de passe saisi avec le sel et l'algorithme du hachage
# enregistré, puis compare les deux résultats
def valider(login: str, mot_de_passe: str) -> Utilisateur | None:
    if not login or not mot_de_passe:
        return None
    utilisateur = utilisateurs.chercher(login)
    if utilisateur is None or not check_password(mot_de_passe, utilisateur.hachage_mot_de_passe):
        return None
    return utilisateur


# le jeton JWT de l'utilisateur, signé avec la clé secrète (HMAC-SHA256)
def creer_jeton(utilisateur: Utilisateur) -> str:
    maintenant = int(time.time())
    # le contenu du jeton : les "claims" (affirmations sur l'utilisateur)
    claims = {
        "sub": utilisateur.login,
        "nom": utilisateur.nom,
        "role": utilisateur.role,
        "iat": maintenant,
        "exp": maintenant + settings.JWT_DUREE_MINUTES * 60,
    }
    return jwt.encode(claims, settings.JWT_SECRET, algorithm="HS256")


# l'utilisateur décrit par un jeton dont la signature et la date d'expiration sont
# valides ; None sinon (jeton falsifié, expiré ou illisible)
def verifier(jeton: str) -> Utilisateur | None:
    try:
        # decode vérifie la signature ET la date d'expiration (claim exp)
        claims = jwt.decode(jeton, settings.JWT_SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return None
    return Utilisateur(claims["sub"], claims["nom"], claims["role"], claims=claims)
    • ligne 5 : la bibliothèque [PyJWT] ;
    • ligne 7 : la fonction [check_password] de [Django] ;
    • ligne 13 : le nom du cookie qui transporte le jeton ;
    • lignes 19-25 : la vérification d'un login et d'un mot de passe. [check_password] lit, dans le hachage enregistré, l'algorithme, le nombre d'itérations et le sel, hache le mot de passe saisi avec eux, et compare les deux résultats (en un temps constant, exemple 23). Un login inconnu et un mot de passe faux donnent le même résultat, [None] ;
    • lignes 29-39 : la fabrication du jeton. Son contenu est un dictionnaire d'affirmations (claims) sur l'utilisateur. Certaines ont un nom normalisé : [sub] (subject), l'identifiant de l'utilisateur ; [iat] (issued at), la date de création ; [exp] (expiration), la date d'expiration. Les dates s'écrivent en secondes écoulées depuis le 1er janvier 1970 ([time.time()] rend ce nombre, avec des décimales, que [int] retire). Les autres affirmations sont libres : ici le nom et le rôle. [jwt.encode] fabrique le jeton et le signe avec l'algorithme [HS256] (HMAC-SHA256, une signature par clé secrète partagée) ;
    • lignes 44-50 : la vérification d'un jeton. [jwt.decode] vérifie la signature et la date d'expiration, puis rend les affirmations. Toute anomalie (jeton falsifié, expiré, mal formé) lève une exception, de la classe [jwt.InvalidTokenError] ou de l'une de ses classes filles, que le bloc [except] intercepte. Le paramètre [algorithms] fixe la liste des algorithmes acceptés : un jeton qui déclarerait un autre algorithme (voire aucun, [none]) serait refusé. Le jeton valide devient un [Utilisateur], sans hachage, avec ses affirmations (paramètre nommé [claims]).

    # securite/middleware.py : l'AUTHENTIFICATION : à chaque requête, qui est l'utilisateur ?

from django.shortcuts import redirect

from . import auth


class Authentification:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # par défaut, le visiteur est anonyme
        request.utilisateur = None
        jeton = request.COOKIES.get(auth.COOKIE)
        if jeton is not None:
            utilisateur = auth.verifier(jeton)
            if utilisateur is None:
                # un jeton invalide (expiré, falsifié) : direction /login, et l'on
                # efface le cookie
                reponse = redirect("login")
                reponse.delete_cookie(auth.COOKIE)
                return reponse
            request.utilisateur = utilisateur
        return self.get_response(request)

    Pour chaque requête, avant la vue :

    • ligne 14 : par défaut, le visiteur est anonyme : [request.utilisateur] vaut [None] ;
    • lignes 15-17 : si la requête porte le cookie du jeton, le jeton est vérifié ;
    • lignes 18-23 : un jeton invalide (expiré ou falsifié) : le middleware répond lui-même, sans appeler la suite, par une redirection vers la page de connexion, et en profite pour effacer le cookie : [delete_cookie] ajoute à la réponse un cookie vide, déjà expiré ;
    • ligne 24 : un jeton valide : l'utilisateur qu'il décrit est rangé dans la requête. Il n'est pas cherché dans la liste des utilisateurs : le jeton suffit, puisqu'il est signé.

    Le middleware ne refuse rien : il établit qui est l'utilisateur, ou constate qu'il est anonyme. C'est l'authentification. Les refus sont l'affaire du contrôle d'accès.

    # securite/decorateurs.py : le contrôle d'accès des vues

from functools import wraps

from django.shortcuts import redirect


# @connexion_requise : la vue n'est exécutée que pour un utilisateur authentifié ; un
# visiteur anonyme est redirigé vers la page de connexion
def connexion_requise(vue):
    @wraps(vue)
    def enveloppe(request, *args, **kwargs):
        if request.utilisateur is None:
            return redirect("login")
        return vue(request, *args, **kwargs)
    return enveloppe

    Le décorateur [@connexion_requise] enveloppe une vue (exemple 08) : si l'utilisateur est anonyme, il répond par une redirection vers la page de connexion, sans appeler la vue ; sinon, il appelle la vue. [django.contrib.auth] fournit un décorateur de même rôle, [@login_required], qui s'appuie sur [request.user].

    # comptes/views.py : connexion, déconnexion, et une page réservée aux utilisateurs
# authentifiés

from django.conf import settings
from django.shortcuts import redirect, render
from django.views.decorators.http import require_GET, require_http_methods, require_POST

from securite import auth
from securite.decorateurs import connexion_requise


@require_GET
def accueil(request):
    return redirect("profil")


# GET : le formulaire ; POST : la connexion (le jeton anti-CSRF a été vérifié par
# CsrfViewMiddleware)
@require_http_methods(["GET", "POST"])
def login(request):
    if request.method == "GET":
        return render(request, "auth/login.html")
    login = request.POST.get("login", "")
    utilisateur = auth.valider(login, request.POST.get("mot_de_passe", ""))
    if utilisateur is None:
        # un message volontairement vague : on ne dit pas si c'est le login ou le mot de passe
        return render(request, "auth/login.html",
                      {"login": login, "erreur": "Login ou mot de passe incorrect."})
    # le jeton, dans un cookie : le JavaScript de la page ne peut pas le lire
    # (httponly) ; il n'accompagne pas les requêtes POST venues d'autres sites
    # (samesite) ; il disparaît en même temps que le jeton expire (max_age)
    reponse = redirect("profil")
    reponse.set_cookie(auth.COOKIE, auth.creer_jeton(utilisateur),
                       max_age=settings.JWT_DUREE_MINUTES * 60, httponly=True, samesite="Lax")
    return reponse


# la déconnexion : POST seulement (un simple lien, placé sur un autre site, ne peut
# pas déconnecter l'utilisateur à son insu) ; on efface le cookie
@require_POST
def logout(request):
    reponse = redirect("login")
    reponse.delete_cookie(auth.COOKIE)
    return reponse


# request.utilisateur : l'utilisateur authentifié, trouvé par le middleware
@require_GET
@connexion_requise

from functools import wraps

from django.core.exceptions import PermissionDenied
from django.shortcuts import redirect


# @connexion_requise : la vue n'est exécutée que pour un utilisateur authentifié ; un
# visiteur anonyme est redirigé vers la page de connexion
def connexion_requise(vue):
    @wraps(vue)
    def enveloppe(request, *args, **kwargs):
        if request.utilisateur is None:
            return redirect("login")
        return vue(request, *args, **kwargs)
    return enveloppe


# @role_requis("ADMIN") : un décorateur PARAMÉTRÉ (cf. exemple 08). La vue n'est
# exécutée que si l'utilisateur authentifié a le rôle demandé ; sinon, l'exception
# PermissionDenied produit une réponse 403 (cf. securite/erreurs.py)
def role_requis(role):
    def decorateur(vue):
        @wraps(vue)
        @connexion_requise
        def enveloppe(request, *args, **kwargs):
            if not request.utilisateur.a_le_role(role):
                raise PermissionDenied(f"rôle {role} requis")
            return vue(request, *args, **kwargs)
        return enveloppe
    return decorateur
    • lignes 23-32 : un décorateur paramétré (exemple 08), [@role_requis("ADMIN")]. L'enveloppe est elle-même enveloppée par [@connexion_requise] : un visiteur anonyme est d'abord envoyé à la page de connexion ; un utilisateur authentifié qui n'a pas le rôle demandé lève l'exception [PermissionDenied] (exemple 24), qui produira une erreur 403 (Forbidden).

# un nombre à virgule, au hasard, entre minimum et maximum
def hasard(minimum: float, maximum: float) -> float:

def svg(texte: str) -> str:
    l, h = LARGEUR, HAUTEUR
    morceaux = [f'<svg xmlns="http://www.w3.org/2000/svg" width="{l}" height="{h}" viewBox="0 0 {l} {h}">',
                '<rect width="100%" height="100%" fill="#f5f7fa"/>']
    # les caractères : chacun agrandi, penché, décalé, et chaque point légèrement
    # déplacé au hasard
    pas = (l - 20) / len(texte)
    for i, caractere in enumerate(texte):
        echelle = hasard(4.6, 5.6)    # taille d'une unité de la grille, en pixels
        angle = hasard(-0.35, 0.35)   # rotation, en radians (environ ±20°)
        cx = 10 + pas * (i + 0.5) + hasard(-3, 3)    # centre du caractère
        cy = h / 2 + hasard(-4, 4)
        for trait in POLICE[caractere]:
            d = []
            # range(0, n, 2) : 0, 2, 4... un point = deux nombres
            for k in range(0, len(trait), 2):
                # point de la grille, centré sur (2, 3), déformé, tourné, placé
                x = (trait[k] - 2 + hasard(-0.2, 0.2)) * echelle
                y = (trait[k + 1] - 3 + hasard(-0.2, 0.2)) * echelle
                px = cx + x * math.cos(angle) - y * math.sin(angle)
                py = cy + x * math.sin(angle) + y * math.cos(angle)
                d.append(f"{'M' if k == 0 else 'L'}{px:.1f} {py:.1f}")
            morceaux.append(f'<path d="{" ".join(d)}" fill="none" stroke="{couleur()}" '
                            f'stroke-width="{hasard(2.2, 3):.1f}" stroke-linecap="round" '
                            f'stroke-linejoin="round"/>')
    # 3 traits de brouillage : des courbes qui traversent l'image
    for _ in range(3):
        morceaux.append(f'<path d="M{hasard(0, 20):.1f} {hasard(5, 45):.1f} '
                        f'C{hasard(30, 60):.1f} {hasard(0, 50):.1f} {hasard(90, 120):.1f} '
                        f'{hasard(0, 50):.1f} {hasard(130, 150):.1f} {hasard(5, 45):.1f}" '
                        f'fill="none" stroke="{couleur()}" stroke-width="1.3"/>')
    morceaux.append("</svg>")
    return "".join(morceaux)

def verifier(id: str, saisie: str) -> bool:
    if not id or not saisie:
        return False
    # get rend la valeur, ou None ; delete retire la réponse du cache, qu'elle soit
    # bonne ou non
    attendu = cache.get(f"captcha.{id}")
    cache.delete(f"captcha.{id}")
    if attendu is None:
        return False    # identifiant inconnu, ou captcha expiré
    # casefold : la chaîne en minuscules, pour une comparaison qui ignore la casse
    return attendu.casefold() == saisie.strip().casefold()

import time

from django.conf import settings
from django.core.cache import cache


# les échecs d'un client sont comptés dans une FENÊTRE de temps fixe : au plus
# LOGIN_MAX_ECHECS échecs par fenêtre de LOGIN_FENETRE_SECONDES secondes
class Limiteur:
    def __init__(self, ip: str):
        self.cle = f"login.{ip}"

    # les secondes à attendre si le client est bloqué, 0 sinon
    def attente(self) -> int:
        etat = cache.get(self.cle)
        if etat is None or etat["echecs"] < settings.LOGIN_MAX_ECHECS:
            return 0
        return max(1, int(etat["fin"] - time.time()))

    # un échec de plus
    def echec(self) -> None:
        etat = cache.get(self.cle)
        if etat is None:
            # une nouvelle fenêtre commence
            etat = {"echecs": 0, "fin": time.time() + settings.LOGIN_FENETRE_SECONDES}
        etat["echecs"] += 1
        # la clé disparaît du cache à la fin de la fenêtre (timeout, en secondes)
        cache.set(self.cle, etat, timeout=max(1, int(etat["fin"] - time.time())))

    # une connexion réussie efface les échecs
    def effacer(self) -> None:
        cache.delete(self.cle)

    Le limiteur compte les échecs d'un client dans une fenêtre de temps fixe : au plus trois échecs par fenêtre de 60 secondes, comptée à partir du premier échec. Chaque client est reconnu à son adresse IP.

    • ligne 13 : la clé du cache, propre au client : [login.127.0.0.1] ;
    • lignes 16-20 : les secondes à attendre si le client est bloqué (le nombre d'échecs a atteint le maximum), 0 sinon. L'état rangé dans le cache est un dictionnaire : le nombre d'échecs, et l'heure de la fin de la fenêtre ;
    • lignes 23-30 : un échec de plus. S'il n'y a pas d'état dans le cache, une nouvelle fenêtre commence. L'état est réécrit, avec une durée de vie qui s'arrête à la fin de la fenêtre : le cache l'oubliera alors de lui-même, et le client repartira de zéro ;
    • lignes 33-34 : une connexion réussie efface les échecs.

    Ce limiteur, écrit pour l'exemple, a une faiblesse : deux échecs simultanés pourraient lire le même état, et n'en compter qu'un. Le cache de [Django] offre des opérations atomiques ([cache.add], qui n'écrit que si la clé n'existe pas, et [cache.incr], qui augmente un nombre), dont se sert la version de l'étude de cas.
