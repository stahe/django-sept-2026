    4. Les gabarits et les formulaires

    Jusqu'ici, les vues fabriquaient elles-mêmes leur réponse : du texte, du JSON, quelques balises HTML écrites dans une chaîne de caractères. Dans une application MVC, fabriquer la page est le rôle de la partie V, que [Django] appelle un gabarit (template) : un fichier qui décrit la page HTML, avec des emplacements pour les données que lui transmet la vue, le contexte du gabarit (le modèle M de MVC, cf. introduction).

    [Django] a son propre moteur de gabarits, et son propre langage de gabarits, le DTL (Django Template Language). Il sait aussi utiliser d'autres moteurs, comme [Jinja2], celui de [Flask] (réglage [TEMPLATES]) ; ce document s'en tient au DTL, que toutes les applications de [Django] utilisent. Un gabarit est un fichier texte, ici du HTML (on lui donne l'extension [.html]), rangé dans un dossier [templates], dans lequel trois sortes de balises sont interprétées sur le serveur :

    • [{{ variable }}] : la valeur d'une variable du contexte, insérée dans la page ;
    • [{% balise %}] : une balise (tag), qui commande le moteur : condition ([{% if %}]), boucle ([{% for %}]), héritage de gabarit ([{% extends %}], [{% block %}]), inclusion ([{% include %}]), fabrication d'une URL ([{% url %}])... ;
    • [{# commentaire #}] : un commentaire, qui n'apparaît pas dans la page produite. Il tient sur une seule ligne ; un commentaire sur plusieurs lignes s'écrit entre les balises [{% comment %}] et [{% endcomment %}].

    Tout le reste est recopié tel quel. Les expressions ne sont pas écrites en [Python], mais dans le langage du DTL, volontairement limité : [modele.titre] désigne la clé [titre] d'un dictionnaire, ou l'attribut [titre] d'un objet, ou l'élément [titre] d'une liste ([Django] essaie dans cet ordre), et, si c'est une méthode, [Django] l'appelle, sans paramètre ; les filtres transforment une valeur ([nom|upper] met un nom en majuscules) ; les balises agissent. C'est tout : le DTL n'a ni opérateurs arithmétiques, ni appels de fonction avec paramètres, ni affectation. C'est voulu : les créateurs de [Django] voulaient que les gabarits puissent être écrits par des graphistes, sans risque de voir la logique de l'application se glisser dans les pages. Un calcul se fait donc en [Python], dans la vue ou dans une méthode d'un objet du contexte, et le gabarit ne fait qu'afficher. Les langages de [Twig] ([Symfony]) et de [Jinja2] ([Flask]), qui s'en sont inspirés, sont plus permissifs : ils calculent ([total / nombre]) et appellent des fonctions avec des paramètres. Enfin, un gabarit n'est pas relu à chaque requête : à sa première utilisation, [Django] l'analyse et le transforme en une liste de nœuds, un objet [Python] qu'il garde en mémoire et réutilise ensuite (en mode debug, il le relit s'il a été modifié). Nous verrons à quoi ressemble cette liste.

from django.shortcuts import render
from django.utils import timezone
from django.views.decorators.http import require_GET

from .modeles import PageModele


# render : le moteur de gabarits fabrique la page à partir du gabarit
# templates/pages/index.html et du CONTEXTE, un dictionnaire des variables mises à
# la disposition du gabarit (ici une seule, modele) ; la page produite est le corps
# de la réponse
@require_GET
def index(request):
    modele = PageModele(
        "Mon premier gabarit",
        "Cette page a été fabriquée par Django, sur le serveur.",
        # l'heure, dans le fuseau horaire de l'application (réglage TIME_ZONE)
        timezone.localtime().strftime("%H:%M:%S"))
    return render(request, "pages/index.html", {"modele": modele})


# le même gabarit avec un autre modèle ; ou un autre gabarit, avec le code 404
@require_GET
def bonjour(request, nom):
    if nom == "inconnu":
        # status : le code de la réponse
        return render(request, "pages/inconnu.html", {"nom": nom}, status=404)
    modele = PageModele(
        f"Bonjour {nom}",
        "Cette fois, le titre de la page vient de l'URL.",
        timezone.localtime().strftime("%H:%M:%S"))
    return render(request, "pages/index.html", {"modele": modele})

    • ligne 21 : le raccourci [render] (du module [django.shortcuts], exemple 04) fait fabriquer la page par le moteur de gabarits. Il reçoit la requête, le nom du gabarit (le chemin du fichier, relatif à l'un des dossiers de gabarits) et le contexte : un dictionnaire, dont chaque clé devient une variable du gabarit, ici une seule, [modele]. [render] rend un objet [HttpResponse], dont le corps est la page fabriquée (de type [text/html]) ;
    • lignes 27-29 : un autre gabarit, avec une autre variable ([nom]). Le paramètre [status] de [render] donne le code de la réponse : ici 404, pour une page d'erreur « maison » ;
    • lignes 30-34 : le même gabarit que la vue [index], avec un autre modèle. C'est l'intérêt de la séparation entre vue et gabarit : un gabarit peut servir à plusieurs vues.

    Les routes ([pages/urls.py]) associent [/] à la vue [index], et [/bonjour/<str:nom>] à la vue [bonjour].

from dataclasses import dataclass


@dataclass(frozen=True)
class Adresse:
    rue: str
    ville: str


@dataclass(frozen=True)
class Produit:
    nom: str
    prix: float
    en_stock: bool


@dataclass(frozen=True)
class BasesModele:
    titre: str
    nom: str
    # str | None : une chaîne, ou None
    surnom: str | None
    html: str
    connecte: bool
    devise: str
    produits: list[Produit]
    panier: list[Produit]
    adresse: Adresse

    # @property : une méthode que l'on lit comme un attribut (modele.total). Le
    # langage des gabarits ne sait pas calculer : les calculs se font en Python
    @property
    def total(self) -> float:
        return sum(p.prix for p in self.produits)

    @property
    def prix_moyen(self) -> float:
        return self.total / len(self.produits)

Le décorateur [@property] fait d'une méthode une propriété : on la lit comme un attribut, sans parenthèses ([modele.total]), et c'est ainsi que le DTL la verra. Les prix sont ici de type [float], pour simplifier (l'exemple 06 a montré pourquoi on leur préfère des centimes entiers).

from django.utils import translation


class FixerLangue:
    def __init__(self, get_response):
        self.get_response = get_response

    # le paramètre ?lang=en de l'URL, le français sinon
    def __call__(self, request):
        langue = "en" if request.GET.get("lang") == "en" else "fr"
        # activate : la langue ACTIVE, que Django utilise pour mettre en forme les
        # nombres et les dates, et pour traduire ses messages
        translation.activate(langue)
        return self.get_response(request)

    Chaque requête a une langue active, qui vaut, par défaut, celle du réglage [LANGUAGE_CODE]. Ici, le paramètre [?lang=en] de l'URL choisit l'anglais, le français est la langue par défaut. Un middleware (exemple 03) la fixe avant chaque vue, par la fonction [translation.activate] : c'est la langue que rendra [get_language], celle dans laquelle [Django] met en forme les nombres et les dates, et traduit ses propres messages (les messages d'erreur des formulaires, par exemple). La langue active est propre au fil d'exécution (thread) qui traite la requête : deux requêtes simultanées peuvent avoir des langues différentes. Elle n'est pas remise à zéro d'une requête à l'autre : c'est pourquoi le middleware la fixe à chaque requête, même pour le français. Le chapitre sur l'internationalisation remplacera ce middleware par celui de [Django], [LocaleMiddleware], et se servira de cette même langue pour traduire les textes.

                      {"formulaire": Formulaire(initial=INITIALES)})
    # un formulaire LIÉ aux données envoyées : il les convertit et les valide
    formulaire = Formulaire(request.POST)
    valide = formulaire.is_valid()
    donnees = None
    if valide:
        # cleaned_data : les valeurs converties par chaque champ ; une liste (champ
        # multiple) est écrite sous forme de texte, ses valeurs séparées par des virgules
        donnees = {cle: ", ".join(valeur) if isinstance(valeur, list) else valeur
                   for cle, valeur in formulaire.cleaned_data.items()}
    # ce que le navigateur a réellement envoyé, champ par champ ; lists() : les
    # couples (nom, liste de toutes les valeurs du champ)
    recu = "\n".join(f"{nom} = [{', '.join(valeurs)}]" for nom, valeurs in request.POST.lists())
    return render(request, "formulaire/formulaire.html", {
        "formulaire": formulaire,
        "recu": recu,
        "valide": valide,
        "donnees": donnees,
    })

    4.6.6. La protection anti-CSRF

    Une attaque CSRF (Cross-Site Request Forgery, falsification de requête inter-sites) consiste, pour un site malveillant, à faire envoyer par le navigateur de sa victime un formulaire vers notre application. Le navigateur y joint les cookies de notre application, et donc la session de l'utilisateur connecté : la requête semble légitime. La parade : chaque formulaire de notre application contient un jeton, aléatoire, que le site malveillant ne peut pas connaître.

    [Django] l'applique à toute l'application, par un middleware, [CsrfViewMiddleware] (ligne 23 du fichier [config/settings.py]). À la fabrication d'une page, la balise [{% csrf_token %}] écrit le champ caché [csrfmiddlewaretoken], et le middleware dépose, avec la réponse, un cookie [csrftoken], qui contient un secret. Pour toute requête qui modifie (POST, PUT, PATCH, DELETE), avant d'appeler la vue, le middleware vérifie que le jeton envoyé (dans le champ [csrfmiddlewaretoken], ou dans l'entête [X-CSRFToken], pour une requête envoyée par [JavaScript]) correspond au secret du cookie. Un site malveillant ne peut ni lire le cookie de notre site, ni lire nos pages : il ne peut pas fabriquer un jeton valide. Si la vérification échoue, la vue n'est pas appelée : [Django] répond lui-même par une erreur 403. C'est une différence importante avec [Symfony], dont le composant Form vérifiait le jeton de chaque formulaire, et laissait l'action décider de la suite : avec [Django], toutes les requêtes POST sont protégées, et une vue ne peut pas oublier de l'être. Le décorateur [@csrf_exempt] dispense une vue de cette vérification (pour une API appelée par d'autres serveurs, par exemple).

class FormulaireBootstrap(forms.Form):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        for champ in self.fields.values():
            champ.widget.attrs["class"] = "form-control"


class InscriptionForm(FormulaireBootstrap):

    # la page (attribut maxlength), pour le navigateur
    nom = forms.CharField(max_length=20, error_messages={
        "required": "Le nom est obligatoire.",
        "max_length": "Le nom ne doit pas dépasser 20 caractères."})
    # EmailField : une adresse valide, avec un nom de domaine complet (exemple.fr, et non exemple)
    email = forms.EmailField(label="Adresse électronique", error_messages={
        "required": "L'adresse électronique est obligatoire.",
        "invalid": "Adresse électronique invalide."})
    # IntegerField : un nombre entier ; une saisie qui n'en est pas un produit l'erreur invalid
    age = forms.IntegerField(label="Âge", min_value=18, max_value=120, error_messages={
        "required": "L'âge est obligatoire.",
        "invalid": "Un nombre entier est attendu.",
        "min_value": "L'âge doit être compris entre 18 et 120 ans.",
        "max_value": "L'âge doit être compris entre 18 et 120 ans."})
    mot_de_passe = forms.CharField(label="Mot de passe", min_length=6, widget=forms.PasswordInput,
                                   error_messages={
                                       "required": "Le mot de passe est obligatoire.",
                                       "min_length": "Le mot de passe doit comporter au moins 6 caractères."})
    confirmation = forms.CharField(label="Confirmation", widget=forms.PasswordInput,
                                   error_messages={"required": "La confirmation est obligatoire."})

    # clean : la validation du formulaire ENTIER, après celle de chaque champ. C'est
    # ici que l'on compare deux champs
    def clean(self):
        donnees = super().clean()
        mot_de_passe = donnees.get("mot_de_passe")
        confirmation = donnees.get("confirmation")
        # les deux champs ont passé leur propre validation, mais diffèrent
        if mot_de_passe and confirmation and mot_de_passe != confirmation:
            # add_error : une erreur, attachée au champ confirmation
            self.add_error("confirmation", "La confirmation ne correspond pas au mot de passe.")
        return donnees

@require_http_methods(["GET", "POST"])
def inscription(request):

    if request.method == "POST":
        formulaire = InscriptionForm(request.POST)

    return render(request, "inscription/inscription.html",
                  {"formulaire": InscriptionForm(), "html5": html5})

# requêtes de tous les utilisateurs (et perdue quand le serveur s'arrête)
_taches = ["Lire le chapitre 3"]

# le serveur traite plusieurs requêtes EN MÊME TEMPS, dans plusieurs fils d'exécution
# (threads) : un verrou garantit qu'un seul à la fois modifie la liste

    # une copie : l'appelant ne peut pas modifier la liste du service
    with _verrou:

    # config/middleware.py : la méthode HTTP d'un formulaire, remplacée par son champ _method

# un formulaire HTML ne sait envoyer que GET et POST. Un formulaire POST qui contient un
# champ caché _method (DELETE, PUT, PATCH) est traité comme une requête de cette méthode
class MethodeSurchargee:
    METHODES = {"DELETE", "PUT", "PATCH"}

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        return self.get_response(request)

    # process_view : Django l'appelle APRÈS le routage, juste avant la vue (et après le
    # process_view des middlewares qui précèdent celui-ci, dont celui qui vérifie le
    # jeton anti-CSRF d'un POST). Rendre None : la requête poursuit son chemin
    def process_view(self, request, view_func, view_args, view_kwargs):
        if request.method == "POST":
            methode = request.POST.get("_method", "").upper()
            if methode in self.METHODES:
                request.method = methode
        return None

import threading

from .modeles import Contact

_contacts = [
    Contact(1, "Marie Durand", "01 23 45 67 89"),
    Contact(2, "Paul Martin", "06 12 34 56 78"),
    Contact(3, "Philippe Jandot", "02 98 76 54 32"),
]
_dernier_id = 3
_verrou = threading.Lock()


def liste() -> list[Contact]:
    with _verrou:
        return list(_contacts)


# le contact, ou None s'il n'existe pas
def lire(id: int) -> Contact | None:
    with _verrou:
        return next((c for c in _contacts if c.id == id), None)


def modifier(id: int, nom: str, telephone: str) -> Contact | None:
    with _verrou:
        # enumerate : les couples (position, élément) de la liste
        for i, contact in enumerate(_contacts):
            if contact.id == id:
                # un contact est immuable (frozen) : on en fabrique un nouveau, qui
                # remplace l'ancien dans la liste
                _contacts[i] = Contact(id, nom, telephone)
                return _contacts[i]
        return None


def ajouter(nom: str, telephone: str) -> Contact:
    # global : la fonction modifie la variable _dernier_id du module (sans ce mot,
    # l'affectation créerait une variable locale)
    global _dernier_id
    with _verrou:
        _dernier_id += 1
        contact = Contact(_dernier_id, nom, telephone)
        _contacts.append(contact)
        return contact


def supprimer(id: int) -> Contact | None:
    with _verrou:
        for i, contact in enumerate(_contacts):
            if contact.id == id:
                # pop retire l'élément i de la liste, et le rend
                return _contacts.pop(i)
        return None

@require_http_methods(["GET", "POST", "DELETE"])
def contact(request, id):
    if request.method == "DELETE":
        return supprimer(request, id)
    contact = contact_ou_404(service.lire(id))
    if request.method == "GET":
        formulaire = ContactForm(initial={"nom": contact.nom, "telephone": contact.telephone})
        return render(request, "contacts/fiche.html", {"contact": contact, "formulaire": formulaire})
    formulaire = ContactForm(request.POST)
    if not formulaire.is_valid():
        return render(request, "contacts/fiche.html", {"contact": contact, "formulaire": formulaire})
    nom = formulaire.cleaned_data["nom"]
    telephone = formulaire.cleaned_data["telephone"]
    # le bouton cliqué est le seul à envoyer son nom : "dupliquer" in request.POST
    # est vrai si c'est lui qui a envoyé le formulaire
    if "dupliquer" in request.POST:
        copie = service.ajouter(f"{nom} (copie)", telephone)
        messages.success(request, f"Le contact [{copie.nom}] a été créé.")
    else:
        service.modifier(id, nom, telephone)
        messages.success(request, f"Le contact [{nom}] a été modifié.")
    return redirect("contacts")


# la suppression ; le jeton anti-CSRF a déjà été vérifié par CsrfViewMiddleware
def supprimer(request, id):
    contact = contact_ou_404(service.supprimer(id))
    messages.success(request, f"Le contact [{contact.nom}] a été supprimé.")
    return redirect("contacts")

// Sans JavaScript, ces formulaires partent simplement sans confirmation.
(() => {
  const modale = document.getElementById('modale-confirmation');
  const message = document.getElementById('modale-confirmation-message');
  let enAttente = null; // le formulaire à envoyer si l'on confirme

  // 1. on intercepte l'envoi des formulaires à confirmer
  document.querySelectorAll('form[data-confirmation]').forEach((formulaire) => {
    formulaire.addEventListener('submit', (evenement) => {
      evenement.preventDefault(); // l'envoi est suspendu
      enAttente = formulaire;
      message.textContent = formulaire.dataset.confirmation;
      modale.classList.remove('d-none'); // la fenêtre apparaît
    });
  });

  // 2. les deux boutons de la fenêtre
  modale.addEventListener('click', (evenement) => {
    const action = evenement.target.dataset.action;
    if (action === 'oui') {
      enAttente.submit(); // envoi, SANS redéclencher l'événement 'submit'
    } else if (action === 'non') {
      modale.classList.add('d-none');
      enAttente = null;
    }
  });
})();
    • ligne 3 : le code est enfermé dans une fonction anonyme, exécutée aussitôt : ses variables ne se mélangent pas à celles des autres scripts de la page ;
    • lignes 4-6 : la fenêtre, l'emplacement du message, et le formulaire en attente de confirmation ;
    • lignes 9-16 : pour chaque formulaire qui porte un attribut [data-confirmation], on intercepte l'événement [submit], déclenché par son envoi. [preventDefault()] suspend l'envoi ; le formulaire est mis en attente, son message ([dataset.confirmation], la valeur de l'attribut [data-confirmation]) est placé dans la fenêtre, qui apparaît ;
    • lignes 19-27 : un seul gestionnaire pour les clics dans la fenêtre : [evenement.target] est l'élément cliqué ; son attribut [data-action] dit de quel bouton il s'agit. « Oui » envoie le formulaire en attente, par la méthode [submit()], qui, contrairement au clic sur un bouton, ne déclenche pas l'événement [submit] (sinon, la fenêtre réapparaîtrait) ; « Non » cache la fenêtre.
